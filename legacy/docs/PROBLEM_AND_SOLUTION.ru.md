# Почему видео открывалось в Windows, но ломалось в VLC — и как это исправить

## Кратко

Файл `01 - Mechanics - Video 1.mp4` **не был повреждён по кодекам**. Проблема была в **структуре контейнера MP4**: аудио и видео лежали в двух огромных неперемешанных фрагментах (сначала весь звук, потом вся картинка). Такой layout часто получается после скачивания/склейки HLS-потока.

- **Windows Media Player / Movies & TV** (Media Foundation) часто такое ещё проигрывает.
- **VLC и другие «строгие» плееры** плохо seek’ают, долго буферизуют или ведут себя нестабильно.

**Решение:** lossless remux в обычный progressive MP4 с чередованием A/V и `moov` в начале файла (`faststart`). Перекодирование не требуется.

---

## Симптомы

| Наблюдение | Комментарий |
|---|---|
| В VLC файл открывается криво / плохо seek / зависания | Типично для «плохого» fMP4 |
| В штатном плеере Windows более-менее играет | Media Foundation терпимее к fragmented MP4 |
| `ffprobe` показывает нормальные H.264 + AAC | Кодеки целы |
| Полный decode через `ffmpeg -f null -` без ошибок | Битрека/кадры не «гнилые» |

Вывод: чинить нужно **контейнер**, а не заново кодировать видео.

## Что показал анализ

### Кодеки и метаданные

- Видео: **H.264 High**, 1280×720, 30 fps, `yuv420p`
- Аудио: **AAC LC**, 48 kHz, stereo
- Длительность ≈ **18:08**
- В тегах энкодера: **`videojs-contrib-hls`**

Тег `videojs-contrib-hls` — сильный признак, что файл собран из HLS-сегментов (или похожим remux-инструментом), а не записан «нормальным» монтажным экспортом.

### Структура контейнера (ISO BMFF / MP4)

Верхнеуровневые боксы исходного файла:

```text
ftyp
moov          ← крошечный, с mvex (movie extends)
moof          ← фрагмент №1 (в основном аудио)
mdat          ← ~33 MB данных аудио
moof          ← фрагмент №2 (видео)
mdat          ← ~309 MB данных видео
```

Ключевые факты:

1. Это **fragmented MP4 (fMP4)**: есть `moof` + `mvex`, а не классическая таблица сэмплов в одном `moov`.
2. Всего **2 фрагмента**, и каждый принадлежит **одному треку**:
   - fragment 0 → track audio, **51039** сэмплов
   - fragment 1 → track video, **32664** сэмплов
3. Аудио и видео **не interleaved** (не чередуются по времени внутри файла).
4. `creation_time` около Unix epoch (`1970-01-01`) — типичный «синтетический» мусор от remux-утилит.

### Почему это ломает плееры

Нормальный progressive MP4 выглядит так:

```text
ftyp
moov          ← полный индекс (куда seek’ать)
mdat          ← аудио и видео кусочками, чередуясь по времени
```

Плеер может:

- быстро найти ключевой кадр;
- параллельно читать звук и картинку;
- начать воспроизведение, не «проглатывая» весь файл.

В проблемном файле:

1. Чтобы начать видео, часто нужно сначала разобрать гигантский audio-`mdat`.
2. Seek по timeline заставляет прыгать между двумя огромными областями файла.
3. Буферизация и синхронизация A/V становятся зависимыми от реализации демуксера.
4. VLC (и ряд других плееров) на таких «двуфрагментных» HLS-remux файлах ведёт себя заметно хуже, чем Windows MF.

Отсюда и расхождение: «в Windows играет, в VLC — нет / почти нет».

## Решение

### Идея

Перепаковать контейнер **без перекодирования** (`-c copy`):

1. Считать оба трека.
2. Записать **один** progressive MP4.
3. Перемешать аудио/видео по времени (interleave).
4. Вынести индекс `moov` в начало (`+faststart`).
5. Нормализовать таймстемпы (`+genpts`, `avoid_negative_ts make_zero`).

Качество и битрейт почти не меняются: копируются те же H.264/AAC пакеты.

### Команда FFmpeg

```bash
ffmpeg -y -fflags +genpts -i "input.mp4" \
  -map 0 -c copy \
  -map_metadata -1 \
  -movflags +faststart \
  -avoid_negative_ts make_zero \
  "output_fixed.mp4"
```

### Через утилиты этого репозитория

```bash
# Диагностика
python analyze_video.py "01 - Mechanics - Video 1.mp4"

# Исправление (auto → remux)
python fix_video.py "01 - Mechanics - Video 1.mp4"
```

Результат: `01 - Mechanics - Video 1_fixed.mp4`.

### Что стало после фикса

```text
ftyp
moov          ← ~1.1 MB полный индекс в начале
mdat          ← один блок, A/V interleaved
```

- `fragmented=False`, `moof=0`
- Один `mdat`
- Файл нормально открывается в VLC
- Decode по-прежнему без ошибок bitstream

Небольшой `start_time` порядка ~0.045 s — обычное явление для AAC priming / H.264 B-frames и само по себе не является поломкой.

## Когда remux недостаточно

Remux чинит **контейнер**. Если анализ/`ffmpeg` показывают повреждения bitstream, редкий пиксельный формат, HEVC без поддержки в плеере и т.п. — нужен **reencode**:

```bash
python fix_video.py "file.mp4" --mode reencode
```

Это уже H.264 `yuv420p` + AAC LC (дольше, с пересжатием).

Альтернатива для «всеядных» плееров: `--mode mkv` (Matroska, тоже stream copy).

## Как распознать ту же болезнь у других файлов

Красные флаги:

- encoder / handler вроде `videojs-contrib-hls`, `hls.js`, youtube-dl/yt-dlp HLS remux без нормализации;
- в структуре много/мало `moof`, но A/V разнесены по огромным `mdat`;
- `moov` крошечный и есть `mvex`;
- Windows играет, VLC — нет;
- `analyze_video.py` выдаёт:
  - `NON_INTERLEAVED_FRAGMENTS` (critical)
  - `FRAGMENTED_MP4` (high)
  - `HLS_REMUX_ENCODER` (high)

Пакетная обработка папки:

```bash
python batch_videos.py . --fix
```
